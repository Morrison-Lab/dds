Brian Hutchinson’s CSCI 481/581 sets the order of topics in these notes, which follow it with his permission; this page covers his module on running deep learning experiments. The exercises are new.

1 Welcome

1.1 Plan for this lecture

Earlier chapters trained networks with settings picked for them: a learning rate, a width, a number of epochs. This lecture is about choosing such settings with experiments, and trusting what the experiments say:

  1. how much a score changes when only the random seed changes;
  2. how to compare two widths fairly when the best learning rate depends on the width;
  3. how to lay out a sweep of learning rates, and check that it was wide enough;
  4. when training longer would help;
  5. what it takes to run the same experiment twice and get the same numbers.

lds’s chapter on machine learning experiments covers the parts that hold for any model: the training, validation and test sets, data snooping, and grid and random search. This lecture adds what is particular to training deep networks.

1.2 The digits

Show code
import pandas as pd
import torch
from torch import nn
import matplotlib.pyplot as plt

digits = pd.read_csv("data/optdigits-test.csv", header=None)
x = torch.tensor(digits.iloc[:, :64].to_numpy(), dtype=torch.float32) / 16
y = torch.tensor(digits[64].to_numpy())
order = torch.randperm(len(x), generator=torch.Generator().manual_seed(481))
train_idx, val_idx = order[:500], order[500:1000]
n_train, n_val = len(train_idx), len(val_idx)
n_unused = len(x) - n_train - n_val
loss_fn = nn.CrossEntropyLoss()


def train_and_score(width, lr, seed, n_epochs=20, batch_size=50):
    # One training run: an MLP with one hidden layer of `width` ReLU units,
    # trained by minibatch SGD. Returns the validation accuracy after each epoch.
    torch.manual_seed(seed)
    net = nn.Sequential(nn.Linear(64, width), nn.ReLU(), nn.Linear(width, 10))
    optimizer = torch.optim.SGD(net.parameters(), lr=lr)
    shuffler = torch.Generator().manual_seed(seed)
    scores = []
    for epoch in range(n_epochs):
        for batch in torch.randperm(len(train_idx), generator=shuffler).split(batch_size):
            rows = train_idx[batch]
            optimizer.zero_grad()
            loss_fn(net(x[rows]), y[rows]).backward()
            optimizer.step()
        with torch.no_grad():
            correct = net(x[val_idx]).argmax(dim=1) == y[val_idx]
        scores.append(correct.float().mean().item())
    return scores


print(n_train, n_val, n_unused)
500 500 797

The exercises use the 1,797 digits of data/optdigits-test.csv [1], each an 8 by 8 image with 64 pixels. 500 random images form the training set and another 500 the validation set. The other 797 stay unused, as a test set would until the model is final. train_and_score() builds an MLP with one hidden layer of width ReLU units. It trains the MLP by minibatch SGD with learning rate lr, 50 images to a minibatch, for 20 epochs unless asked for more. It returns the accuracy on the validation set after each epoch.

2 Settings and seeds

2.1 What training does not learn

Exercise 1 (Settings that training does not learn)

Exercise 1 (Settings that training does not learn) List the numbers that train_and_score() uses but SGD never changes.

Solution 1

Solution 1. SGD changes only the weights and biases of the two nn.Linear layers. These numbers are set before training starts, and stay as set:

  • the width of the hidden layer, width;
  • the learning rate, lr;
  • the number of epochs, n_epochs;
  • the minibatch size, batch_size;
  • the random seed, seed;
  • the sizes of the training and validation sets, 500 and 500.

The first four are hyperparameters: settings that we choose, rather than learn from the data. So are choices that are not numbers, such as SGD itself, the ReLU activation and the single hidden layer. The seed is not a setting of that kind. No seed suits new data better than another, so a seed chosen for its validation score has been fitted to noise. The set sizes are a choice about the data, not the model.

3 Comparing settings fairly

3.1 Two widths

Exercise 4 (A fair comparison)

Exercise 4 (A fair comparison) A classmate wants to know whether a network of width 512 classifies the digits better than one of width 8. They train one of each with learning rate 0.1. What could make that comparison unfair?

Solution 4

Solution 4. Nothing says that one learning rate is best for both widths. If 0.1 suits width 512 and is too small for width 8, the comparison measures how well each width suits 0.1, as well as the width itself. A fair comparison tunes the learning rate for each width on its own, and compares each width at its own best rate. One run of each has the problem of Solution 3 too, so each setting gets several seeds.

3.2 A sweep for each width

Exercise 5 (A learning-rate sweep)

3.3 Three roles

Definition 1 (Scientific hyperparameter)

Definition 1 (Scientific hyperparameter) A scientific hyperparameter of an experiment is a hyperparameter whose effect on the model’s performance the experiment is meant to measure [2].

Example 1 (The width in the sweep)

Example 1 (The width in the sweep) In Solution 5, the width is the scientific hyperparameter: the sweep asks whether width 512 classifies the digits better than width 8.

Definition 2 (Nuisance hyperparameter)

Definition 2 (Nuisance hyperparameter) A nuisance hyperparameter of an experiment is a hyperparameter that the experiment tunes for each value of its scientific hyperparameters, so that those values are compared fairly [2].

Example 2 (The learning rate in the sweep)

Example 2 (The learning rate in the sweep) In Solution 5, the learning rate is a nuisance hyperparameter. The sweep tunes it for each width, 8 and 512, and compares the widths at their own best rates.

Definition 3 (Fixed hyperparameter)

Definition 3 (Fixed hyperparameter) A fixed hyperparameter of an experiment is a hyperparameter that keeps one value throughout the experiment [2]. The experiment’s conclusions hold for that value, and may not hold for others.

Example 3 (What the sweep held fixed)

Example 3 (What the sweep held fixed) In Solution 5, the fixed hyperparameters include the minibatch size of 50, the 20 epochs, the single hidden layer and the choice of SGD. So the sweep shows that width 512 beats width 8 after 20 epochs of SGD with minibatches of 50. It does not show it for 5 epochs, or for Adam.

Remark 1 (A role belongs to an experiment)

Remark 1 (A role belongs to an experiment). One hyperparameter can play a different role in each experiment [2]. The learning rate is a nuisance hyperparameter in Solution 5. An experiment that asks whether learning-rate warmup helps makes the warmup’s length a scientific hyperparameter, and still tunes the learning rate as a nuisance. An experiment that cannot afford to tune the learning rate makes it a fixed hyperparameter, and its conclusions then come with that caveat [2].

4 Laying out a sweep

4.1 Spacing the rates

Exercise 6 (Spacing the rates)

Exercise 6 (Spacing the rates) Each learning rate in Exercise 5 is about 3 times the one before it. What would go wrong with seven rates spread evenly from 0.003 to 3?

Solution 6

Solution 6.

Show code
import numpy as np

even_rates = np.linspace(0.003, 3, 7)
print(even_rates.round(4))
[0.003  0.5025 1.002  1.5015 2.001  2.5005 3.    ]

Evenly spread rates go up by 0.4995 at each step, so the second is already 0.5025. Nothing between 0.003 and 0.5025 would be tried, and that interval holds width 8’s best learning rate, 0.3, and every rate at which width 512 was still improving in Figure 1. Good learning rates can differ by factors of 10 or more, so a sweep spaces them by a constant factor: evenly on a log scale. Random search draws a learning rate the same way, uniform on its logarithm (lds).

4.2 The edge of the sweep

Exercise 7 (The edge of the sweep)

Exercise 7 (The edge of the sweep) Suppose the sweep in Solution 5 had stopped at learning rate 1. What would its result for width 512 leave unknown?

Solution 7

Solution 7. Width 512’s best learning rate would then be the largest one tried. A larger rate might do better still, and the sweep could not say. When the best value sits at the edge of the range searched, the range is suspect, and the next step is to extend it in that direction [2]. The actual sweep went one step further, to 3, where width 512’s mean validation accuracy drops to 0.088, about the 0.1 of guessing one digit of ten. So the rate that suits width 512 best lies between 0.3 and 3, and a finer sweep in that range could pin it down.

Definition 4 (Compute-bound)

Definition 4 (Compute-bound) Training is compute-bound when how long we are willing to train limits the model’s performance, rather than the amount of data or anything else [2]. Then training longer, with the hyperparameters tuned for the longer run, improves the validation performance.

At learning rate 0.03, width 512’s validation accuracy rises from 0.880 after 20 epochs to 0.914 after 100. That run alone would suggest that 20 epochs hold the model back. But at its best learning rate the network gets 0.948 in 20 epochs, more than the slow run gets in 100. Tuned for 100 epochs instead, over learning rates 0.1, 0.3 and 1, the best 100-epoch run reaches 0.954, less above the 20-epoch run than the seed alone moved width 64 in Solution 2. Longer training does not help, so training this network on these 500 images is not compute-bound. Something other than training time limits it.

Remark 2 (Spending a fixed budget)

Remark 2 (Spending a fixed budget). The sweep in Solution 5 trained 42 networks for 20 epochs each, 840 epochs in all. One 100-epoch run of one network takes as many epochs as 5 of those trials. Here, where training is not compute-bound, the extra 80 epochs in Solution 8 bought nothing, and the same 80 epochs would have paid for 4 more trials of the same width, such as more seeds or more learning rates. When training is compute-bound, Godbole et al. [2] still advise against making every trial as long as the budget allows. They tune in rounds, starting with many short runs to find good settings and ending with a few long runs at the best of them.

6 Running it again

6.1 Where the randomness comes from

Exercise 9 (Where the randomness comes from)

Exercise 9 (Where the randomness comes from) List every random draw that a run of train_and_score() depends on.

Solution 9

Solution 9.

  • The starting weights. torch.manual_seed(seed) seeds PyTorch’s global random number generator, and each nn.Linear draws its starting weights and biases from it.
  • The order of the minibatches. shuffler, a generator of its own seeded with seed, draws a new order of the training images in each epoch.
  • The split. order, drawn once outside the function from a generator seeded with 481, decides which images are for training and which for validation. Every run shares it, so the runs differ in their seeds and settings but not in their data.

A network with dropout would draw one more random mask at each step, from the global generator.

Remark 3 (Seeds are not enough)

Remark 3 (Seeds are not enough). PyTorch’s documentation warns that completely reproducible results are not guaranteed across PyTorch releases or platforms, or between a CPU and a GPU, even with identical seeds [3]. Some GPU operations are nondeterministic, and torch.use_deterministic_algorithms(True) makes PyTorch choose deterministic ones, often more slowly, or raise an error where it has none [3]. So record more than the seed: the hyperparameters, the versions of the code, the data and the libraries, and the trained weights themselves. lds’s section on tracking runs gives the habits that make a result traceable a month later.
